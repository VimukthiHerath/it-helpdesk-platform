## 3. AC2 – Broker Restart & Message Persistence Log

### Restart Procedure

| Step | Action | Command |
|------|--------|---------|
| 1 | Produce canary message | `kafka-console-producer.sh ... --topic resilience-health-check` |
| 2 | Record pre-restart offset | `kafka-run-class.sh kafka.tools.GetOffsetShell ...` |
| 3 | Restart broker | `docker restart local-kafka` |
| 4 | Wait for readiness | Health probe polling every 2 s (max 30 s) |
| 5 | Consume & verify | `kafka-console-consumer.sh --from-beginning ...` |

### Evidence Fields (populated by script at runtime)

| Field | Value |
|-------|-------|
| Restart Timestamp | *(see script output)* |
| Canary Topic | `resilience-health-check` |
| Canary Message | `resilience-canary-<yyyyMMddHHmmss>` |
| Offset Before Restart | *(see script output)* |
| Broker Ready After | *(±N seconds)* |
| Offset After Restart | *(should equal or exceed pre-restart offset)* |
| Message Found Post-Restart | **PASS** / FAIL |

> The persistent Docker named volume (`kafka_data`) ensures that KRaft segment files survive container lifecycle events.  
> Even when the container is fully stopped and restarted, the volume is re-attached and Kafka re-reads the existing log segments.

## 5. How to Generate Fresh Evidence

The script that automated this was removed in Sprint 4. To collect fresh evidence, run the
same checks by hand against the local broker (`docker compose up -d kafka`): list the
topics and consumer groups with `kafka-topics.sh` / `kafka-consumer-groups.sh` inside the
`local-kafka` container, check the data volume's disk usage, restart the container, and
confirm the topics and committed offsets are still there.

The script will:
1. Check disk utilisation inside the container.
2. Produce a timestamped canary, restart the broker, consume, and verify.
3. HTTP-probe each of the 5 microservice `/health` endpoints.
4. Overwrite this file (`docs/KAFKA_STORAGE_AUDIT_SPRINT3.md`) with live results.
